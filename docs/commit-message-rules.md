# Правила составления commit message

Документ описывает правила для трёх разных случаев:

- обычный коммит в свою фича-ветку;
- мерж фича-ветки в `dev`;
- мерж `dev` в `main`.

Общее правило для всех случаев: Codex не делает коммиты самостоятельно, а только пишет готовый текст commit message на русском языке.

## Общие правила

- Опираться только на реальные изменения в git, а не на догадки.
- Перед описанием смотреть фактуру: staged diff, список коммитов ветки, diff/stat или прошлые merge-коммиты, в зависимости от сценария.
- Не описывать изменения, которых нет в соответствующем наборе изменений.
- Писать результат на русском языке.
- Формулировать пункты с точки зрения результата для проекта: что добавлено, исправлено, изменено, обновлено.
- Не перегружать сообщение именами файлов, если файл сам по себе не важен для понимания изменения.
- Указывать тесты, миграции, инструкции и настройки только если они действительно входят в изменения.
- Если номер задачи известен, использовать формат `[Задача N] Название`.
- Если номер задачи неизвестен, использовать формат `[Задача] Название`.
- Не придумывать номер задачи.
- Не использовать неопределённые формулировки вроде «разные правки», «улучшения», «фикс багов» без раскрытия сути.

## Обычный коммит в свою фича-ветку

Этот формат используется, когда нужно написать commit message по изменениям в staged area.

### Что смотреть

- `git status --short`
- `git diff --cached --stat`
- `git diff --cached --name-status`
- `git diff --cached`

Описывать нужно только staged changes. Unstaged и untracked изменения не входят в commit message, если они не добавлены в staged area.

### Формат

```text
[Задача N] Короткое название задачи
- Добавлено ...
- Исправлено ...
- Обновлено ...
```

Если номер задачи неизвестен:

```text
[Задача] Короткое название задачи
- Добавлено ...
- Исправлено ...
- Обновлено ...
```

### Правила содержания

- Заголовок должен описывать основную задачу, а не отдельный файл или техническую операцию.
- Обычно достаточно 3-8 пунктов.
- Если изменения маленькие, можно оставить 1-3 пункта.
- В пунктах нужно перечислить значимые изменения из staged diff.
- Если есть backend, frontend, документация и тесты, их можно перечислить отдельными пунктами.
- Если есть миграция базы данных, её нужно явно упомянуть.
- Если есть тесты, написать, какие проверки добавлены или обновлены.
- Не писать клиентские патчноуты: это внутренний commit message для фича-ветки.
- Не добавлять секцию `Подробности:`, если задача одна и список короткий.

### Пример

```text
[Задача 125] Обработка ошибок документов ИПУ
- Добавлена возможность исправлять РСО у документов ИПУ без повторной загрузки файла.
- Обновлено отображение ошибок обработки с разделением предупреждений и критичных проблем.
- Добавлено логирование действий пользователя при исправлении документа.
- Добавлены функциональные тесты исправления РСО в документах ИПУ.
```

## Мерж фича-ветки в `dev`

Этот формат используется, когда нужно написать commit message для merge-коммита фича-ветки в `dev`.

### Что смотреть

- Текущую целевую ветку и ветку-источник.
- Уникальные коммиты фича-ветки относительно `dev`.
- Сообщения коммитов фича-ветки.
- Общий состав diff между `dev` и фича-веткой.
- Список изменённых файлов, чтобы не пропустить документацию, тесты, миграции и настройки.

Типовые команды:

```bash
git log --oneline origin/dev..origin/feature-branch
git log --format=%B origin/dev..origin/feature-branch
git diff --stat origin/dev...origin/feature-branch
git diff --name-status origin/dev...origin/feature-branch
```

Важно не описывать коммиты, которые уже есть в `dev`. Источник правды — уникальные изменения фича-ветки относительно целевой ветки.

### Формат для одной задачи

Если фича-ветка содержит одну задачу:

```text
[Задача N] Название задачи
- Добавлено ...
- Исправлено ...
- Обновлено ...
- Добавлены тесты ...
```

Если изменений много, можно добавить секцию `Подробности:`.

### Формат для нескольких задач

Если в фича-ветке несколько разных задач, сначала нужно перечислить задачи, а потом раскрыть изменения по группам.

```text
[Задача N] Название первой задачи
[Задача M] Название второй задачи
[Задача] Название задачи без номера

Подробности:
1. Первая задача:
- Добавлено ...
- Исправлено ...

2. Вторая задача:
- Добавлено ...
- Обновлено ...

3. Задача без номера:
- Добавлено ...
- Добавлены тесты ...
```

### Правила содержания

- Верхний список должен показывать все задачи, которые входят в merge.
- Если задача без номера, использовать `[Задача]`.
- В `Подробности:` группировать изменения по задачам или крупным направлениям.
- Внутри группы писать понятные пункты результата: API, UI, расчёты, обработка документов, инструкции, тесты.
- Не смешивать независимые задачи в один общий список.
- Не превращать сообщение в клиентские патчноуты: это merge в рабочую ветку `dev`, поэтому можно упоминать backend-модули, API, права доступа, тесты и технические детали, если они важны.
- Не включать изменения из `dev`, которые попали в фича-ветку через обратный merge или rebase.
- Если ветка содержит только документацию, писать это прямо и не раздувать сообщение.
- Если ветка содержит исправление регрессии, описать симптом и результат исправления.

### Пример

```text
[Задача 107] Инструкция: Полнота данных
[Задача 125] Обработка документов ИПУ и ОДН

Подробности:
1. Инструкции:
- Актуализирована инструкция по полноте данных.
- Добавлены разделы по ИПУ и ОДПУ.

2. Обработка документов:
- Добавлены исправления документов ИПУ без РСО через выбор РСО.
- Ошибки и предупреждения обработки разделены по критичности.
- Добавлено логирование истории действий при исправлении документов.
- Добавлены функциональные тесты исправления проблем обработки.
```

## Мерж `dev` в `main`

Этот формат используется для релизного merge-коммита из `dev` в `main`.

`main` — релизная ветка, поэтому commit message должен быть похож на патчноуты для клиентов.

### Что смотреть

- Прошлые merge-коммиты в `main`, чтобы повторить формат релизных сообщений.
- Уникальные коммиты `dev` относительно `main`.
- Merge-коммиты фича-веток, которые входят в релиз.
- Общий diff/stat между `main` и `dev`.

Типовые команды:

```bash
git log --oneline --merges origin/main
git log --format=%B origin/main..origin/dev
git diff --stat origin/main...origin/dev
git diff --name-status origin/main...origin/dev
```

### Формат

Формат должен быть клиентским и релизным. Нужно группировать изменения по пользовательской ценности.

```text
Релиз: краткое название или основная тема

Добавлено:
- ...
- ...

Улучшено:
- ...
- ...

Исправлено:
- ...
- ...

Документация:
- ...
```

Если в проекте последние merge-коммиты в `main` используют другой формат, нужно повторить актуальный формат проекта.

### Правила содержания

- Писать так, чтобы сообщение можно было показать клиенту.
- Делать акцент на пользовательских возможностях, исправлениях и заметных изменениях поведения.
- Группировать изменения по смыслу: добавлено, улучшено, исправлено, документация.
- Не перегружать сообщение внутренними деталями реализации, названиями приватных классов, функциями, тестовыми файлами и служебными изменениями.
- Технические детали оставлять только если они важны для клиента или эксплуатации: права доступа, миграции данных, изменения импорта, новые инструкции, важные ограничения.
- Упоминать исправления через понятный клиенту симптом: что раньше работало неправильно и что теперь исправлено.
- Указывать новые страницы, новые отчёты, новые действия пользователя и изменения в интерфейсе.
- Не перечислять каждый commit из `dev` отдельно, если это не помогает понять релиз.
- Не включать чисто внутренние тесты и рефакторинг как отдельные пункты, если они не меняют поведение продукта.
- Если есть breaking changes, изменения настроек, миграции или действия после релиза, выделять их отдельным блоком.

### Пример

```text
Релиз: обработка показаний и расчёт КР СОИ

Добавлено:
- Добавлена страница обработки документов ИПУ с просмотром причин ошибок и действиями исправления.
- Добавлен сводный расчёт КР СОИ по всем ресурсоснабжающим организациям.
- Добавлены инструкции по работе с показаниями ИПУ и расчётом КР СОИ.

Улучшено:
- Обновлена таблица расчёта КР СОИ: добавлены РСО, ресурс, единицы измерения и сводный режим.
- Улучшена обработка документов ОДН и ИПУ: ошибки и предупреждения разделены по критичности.

Исправлено:
- Исправлен расчёт электроэнергии в КР СОИ.
- Исправлена обработка адресов нежилых помещений в выгрузках УВК.
```
